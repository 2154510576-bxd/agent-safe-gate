# 飞书镜像对接

本文说明**本机账号权威与飞书用户表之间的关系**：谁是权威、什么时机同步、写哪些字段、口令怎么处理、失败了会怎样。

| 项 | 说明 |
| --- | --- |
| 相关代码 | `AiApprovalServer/Services/FeishuMirror.cs`（HTTP 与字段映射）、`Services/UserService.cs`（镜像钩子）、`Core/AppConfig.cs`（`FeishuOptions` 与凭证解析）、`Api/AdminApi.cs`（管理端重试与取回演示口令） |
| 账号权威 | `App_Data/users.json`。登录、鉴权、权限判断**只读本机文件**，飞书表不参与任何判定 |
| 配置样例 | `AiApprovalServer/config/secrets.local.example.json`（凭证模板，不含真实值） |
| 相关文档 | [账号与权限设计.md](账号与权限设计.md)（账号字段与四角色矩阵）、[API参考.md](API参考.md)（接口细节） |

---

## 1. 为什么要镜像

主服务器是本项目的账号权威：账号、角色、口令散列、停用状态全部落在本机 JSON。
协作方的前端（飞书版小财奴）按"账号存在飞书用户表里"的方式工作，为了让**两边看到的数据一致**，
本服务在账号发生变化时把账号资料写进飞书用户表，这就是"镜像"。

镜像的定位是 **best-effort（尽力而为）**：

| 原则 | 具体表现 |
| --- | --- |
| 不影响业务 | 镜像失败绝不改变注册、登录、改密、改角色、停用/启用、删除的返回结果 |
| 不阻塞请求 | 超时短（默认 3000ms）、重试少（默认 1 次），且在网络调用前就已提交本机 JSON 的写入 |
| 可观测 | 失败写审计 `feishu.mirror.failed` 与服务端 warning 日志，并把原因落到该账号的 `mirrorState` / `mirrorError` |
| 可补救 | 管理端可对单个账号"重试镜像" |
| 可关闭 | 未配置凭证时整个镜像链路被跳过（`mirrorState = skipped`），账号功能照常可用 |

> 换句话说：**镜像挂了，系统照常工作**。这也是"允许静默失败"的含义——用户看不到任何错误，管理员在后台能看到状态与原因。

## 2. 镜像的触发时机

触发点全部在 `Services/UserService.cs`：

| 触发时机 | 调用点 | 传给镜像的明文口令 | 备注 |
| --- | --- | --- | --- |
| 创建账号 | `CreateAsync` 末尾 | 有（刚创建时的明文口令） | 这是 `demo` 模式生成演示口令的唯一时机 |
| 修改/重置口令 | `ChangePasswordAsync` 末尾 | 有（新明文口令） | 会先清空 `mirrorPasswordCipher` / `mirrorHashHex` / `mirrorSaltHex`，再重新生成 |
| 变更角色 | `SetRoleAsync` 末尾 | 无 | 沿用既有口令材料，只更新「角色」列等资料 |
| 停用 / 启用 | `SetDisabledAsync` 末尾 | 无 | 同步「账号状态」列 |
| 手动重试 | `POST /api/admin/users/{id}/mirror-retry` → `RetryMirrorAsync` | 无 | 用既有材料重试；不会重新生成演示口令 |
| 删除账号 | 无镜像 | —— | 删除只作用于本机权威库，**飞书镜像行需要人工清理**（接口响应里已提示） |

**登录不会触发镜像**：登录成功只更新本机的 `lastLoginAt` / `lastLoginIp`，飞书表里的「最后登录时间」可能落后于本机。

镜像的写入策略（`FeishuMirror.SyncAsync`）：

- 账号有 `mirrorRecordId` → `PUT .../records/{record_id}` 更新该行；
- 没有 → `POST .../records` 新建，并把返回的 `record_id` 存回账号；
- **更新失败时（常见于对面把行删了）自动降级为"重新创建一次"**；再失败才标记 `failed`。

## 3. 字段映射

本机字段 → 飞书用户表列名（`FeishuMirror.BuildFields`）：

| 本机字段 | 飞书用户表列 | 值形态 |
| --- | --- | --- |
| `employeeId` | `工号` | 文本，`E` + 4 位 |
| `displayName` | `姓名` | 文本 |
| `userName` | `用户名` | 文本 |
| `role` | `角色` | **单选**，写的是飞书侧的中文标签（见下） |
| `disabled` | `账号状态` | **单选**，`停用` / `启用` |
| `createdAt` | `创建时间` | 日期，**毫秒时间戳**（UTC） |
| `lastLoginAt`（有值才写） | `最后登录时间` | 日期，**毫秒时间戳** |
| `mirrorHashHex` / `mirrorSaltHex` | `密码哈希` / `盐` | 十六进制字符串，内容取决于口令模式（见第 4 节） |

角色映射（`Roles.ToFeishuLabel`）：飞书用户表的「角色」单选只有三个选项，四角色按下面归并——

| 本机角色 | 飞书「角色」列 |
| --- | --- |
| `superadmin` | `管理员` |
| `admin` | `管理员` |
| `finance` | `财务` |
| `employee` | `员工` |

> 也就是说：**超级管理员在飞书侧显示为「管理员」**。这是有意的取舍——不向协作方的表结构暴露第四个角色，
> 同时保证"看起来一致"。

字段名与选项值必须与协作方的表结构**逐字一致**（含空格），否则飞书写入会报错；当前值以协作方文档
`飞书字段对接手册.md` / `TABLE_SETUP.md` 与飞书表实际配置为准。

## 4. 口令的三种镜像模式

配置项 `Feishu:MirrorPasswordMode`，取值 `demo`（默认）/ `real` / `none`。
模式只在**准备写进飞书的口令材料**时起作用（`FeishuMirror.PrepareCredentials`），与本机账号的真实口令无关。

| 模式 | 写进飞书的「密码哈希」「盐」 | 协作方能否用它登录 | 安全含义 |
| --- | --- | --- | --- |
| `demo`（默认） | **随机生成的"演示口令"**的 PBKDF2 哈希与盐 | 能（拿到演示口令即可） | 飞书表即使被整表导出，也**爆不出用户的真实口令**（演示口令与真实口令无关，且每次改密都会重新生成） |
| `real` | **真实口令**的等价哈希与盐 | 能（用户用真实口令即可在对面登录） | 等于把口令材料放到了飞书表：该表被拖库即获得可离线爆破的散列，安全性最差 |
| `none` | 不写这两列 | 不能 | 只镜像账号资料；本机 `mirrorHashHex` / `mirrorSaltHex` 保持为空 |

### 4.1 为什么默认 `demo`

1. **真实口令不出本机**：`real` 模式会把真实口令的散列写进一张协作方可以直接打开、导出、共享的多维表格；
   一旦该表泄露，攻击者就拿到了离线爆破的靶子（尤其当用户口令较弱时）。`demo` 模式下泄露的只是与真实口令无关的随机串。
2. **"看起来一致"的目标仍然达成**：协作方需要的是"这张表里有一行账号、能用某个口令登录我们的前端"。
   演示口令满足这个需求，且可以随时交给对方。
3. **改密即轮换**：本机口令一旦变更，`ChangePasswordAsync` 会清空旧的演示口令材料并重新生成，不会出现"旧演示口令永远有效"。

### 4.2 演示口令怎么取回

演示口令**明文以 AES-256-GCM 加密**存放在本机账号记录的 `mirrorPasswordCipher` 中（AAD 为 `mirror-demo-password:<userId>`），
加密密钥由账号密钥域单独派生（`AppConfig.DeriveKey("mirror-demo-password")`，与邮箱等其它用途的密钥域隔离）。取回方式：

| 方式 | 位置 | 说明 |
| --- | --- | --- |
| 创建账号的响应 | `POST /api/auth/register` 与 `POST /api/admin/users` 的 `mirrorDemoPassword` 字段 | 创建时直接给出，另有 `mirrorNote` 说明镜像结果 |
| 管理端查询 | `GET /api/admin/users/{id}/mirror-password` | 需要 `account.manage` 权限；返回 `demoPassword` 与 `hint`，并写审计 `user.mirror-password` |
| 重置口令的响应 | `POST /api/admin/users/{id}/reset-password` 的 `mirrorDemoPassword` | 重置后演示口令同步轮换 |

口令生成规则（`FeishuMirror.GenerateDemoPassword`）：长度取 `Feishu:DemoPasswordLength`（默认 12，代码内钳制 8~32），
字符表刻意去掉了易混淆字符 `0/O/1/l/I`，便于人工转抄给协作方。

> 镜像使用的 PBKDF2 参数必须与协作方前端一致，否则对面校验不过：`Feishu:MirrorPbkdf2Iterations` 默认 **100000**、
> 16 字节盐、SHA-256、32 字节输出、十六进制编码（`FeishuMirror.HashForFeishu`）。
> 注意这与本机账号的散列参数（21 万次迭代、base64）**不同**，两者互不影响。

## 5. 换票、超时、重试与出站白名单

### 5.1 tenant_access_token

- 端点：`{Feishu:BaseUrl}` + `/open-apis/auth/v3/tenant_access_token/internal`，用 `app_id` + `app_secret` 换取。
- 缓存：换到的令牌缓存在进程内，有效期取返回的 `expire`（默认 7200 秒）**提前 60 秒**过期（最少 30 秒），到期自动续期。
- 并发：用一个 `SemaphoreSlim` 串行化换票，避免并发请求同时换票。
- 后续所有 Bitable 请求带 `Authorization: Bearer <token>`。

### 5.2 超时与重试

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `Feishu:TimeoutMs` | 3000 | 单次 HTTP 超时（同时用于 `HttpClient.Timeout` 与 `ConnectTimeout`，最小 500ms） |
| `Feishu:MaxRetries` | 1 | 失败重试次数（不含首次），仅对 `HttpRequestException` 与超时生效，重试间隔 200ms；**每次尝试都用工厂函数重建请求对象**，因此重试能真正重新发送（不会出现"同一请求已发送"的异常） |

失败最终都会转成 `MirrorResult.Fail`，不会抛到业务层。

### 5.3 出站白名单与本地假飞书

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `Feishu:AllowedHosts` | `open.feishu.cn` | 出站主机白名单（逗号/分号/空格分隔）。不在白名单的主机直接抛错、请求根本不发出去 |
| —— | 固定放行 | `127.0.0.1`、`localhost`、`::1`：便于把 `Feishu:BaseUrl` 指向本机假飞书做离线验收 |
| `Feishu:BaseUrl` | `https://open.feishu.cn` | 飞书 API 基地址。本地验收时指向 `tests/mock-feishu.mjs` 监听的地址（形如 `http://127.0.0.1:<port>`），整条链路即可离线跑通且**不会误写真实表** |

> 白名单校验发生在发送之前（`FeishuMirror.HostAllowed` / `SendAsync`），因此"配错域名"的失败不会产生任何外发流量。

## 6. 镜像状态机

每个账号记录里都带镜像状态，取值与含义：

| `mirrorState` | 含义 | 触发条件 |
| --- | --- | --- |
| `pending` | 尚未尝试（模型默认值） | 账号刚创建、镜像还没走完 |
| `synced` | 已同步 | 创建或更新成功；同时写入 `mirrorRecordId`、`mirrorAt`，清空 `mirrorError` |
| `failed` | 同步失败（已静默处理） | 换票失败、写入返回非 0 code、网络异常、超时、出站主机不在白名单等 |
| `skipped` | 未启用，跳过 | `FeishuConfigured` 为假（凭证不齐），`mirrorError` 写明"未配置飞书（Feishu:AppId/AppSecret/AppToken/UserTableId）" |

> **一处口径差异（以代码为准）**：未配置飞书时，`UserService.MirrorAsync` 在 `FeishuMirror.Enabled` 为假时直接返回 `skipped`，
> 不经过落盘步骤，因此创建账号的**接口响应**里 `mirrorState = "skipped"`，而 `users.json` 里保存的仍是初始值 `"pending"`。
> 管理端看到未配置飞书的历史账号停留在 `pending` 属正常现象。

失败时的落盘与审计：

- `mirrorState = failed`、`mirrorError`（原因截断 300 字符）、`mirrorAt` 更新；
- 服务端日志：`飞书镜像失败（不影响业务）：<用户名> <原因>`（warning 级）；
- 审计：`feishu.mirror.failed`（`outcome = FAILED`），明细写明"已静默处理"；
- 成功时审计：`feishu.mirror.sync`（`outcome = SUCCESS`，包含角色与返回的 `record_id`）。

管理端重试：`POST /api/admin/users/{id}/mirror-retry`（需 `account.manage`），返回
`{ ok, skipped, error, message }`——`ok` 为假、`skipped` 为真都表示"业务不受影响"。

`GET /api/admin/users` 的每条记录都带 `mirrorState`、`mirrorError`、`mirrorAt`、`mirrorRoleLabel`，便于后台直接展示与重试。

## 7. 外部账号防护

**飞书表里"有、本机没有"的账号，永远不能登录本系统。** 依据是登录路径：

- `UserService.LoginAsync` 只调用 `FindByNameAsync`，而它读取的是 `App_Data/users.json`；
- 全流程没有任何"口令校验回落到飞书表"的分支（本机账号不存在时直接走 dummy PBKDF2 并返回统一失败文案）；
- 因此对面的表里新增一行账号，不会在本系统产生任何可登录身份；即使对方写了 `密码哈希`/`盐`，也不会被本机读取校验。

这样设计的必要性：飞书表对协作方是可直接编辑的多维表格。如果登录会回落到它，
"往表里插一行"就等于在系统里开一个后门，权限矩阵与账号策略（不能改自己角色、必须保留最后一个超管等）都会被绕过。

**启动时会主动发现并留痕**（`Program.cs`，条件：`FeishuConfigured` 为真且 `Feishu:DetectForeignAccounts` 为真，默认开启）：

| 步骤 | 行为 |
| --- | --- |
| 拉取 | `FeishuMirror.ListUsersAsync()` 读取飞书用户表（`page_size=200`），取出每行的 `用户名` / `工号` / `姓名` / `角色` |
| 比对 | 与本机 `users.json` 的用户名集合做**大小写不敏感**比较，找出"飞书有、本机没有"的账号 |
| 留痕 | 对每一个外部账号写一条审计：动作 `feishu.mirror.foreign-account`，`outcome = IGNORED`，`target` 为用户名，明细含姓名、工号、对面角色，并注明"本系统登录只读本机 JSON，该账号无法登录" |
| 提示 | 控制台打印 `[镜像] 发现 N 个仅存在于飞书用户表的账号，已记审计并忽略（它们无法登录本系统）` |
| 处置 | **不做任何账号创建或权限授予**：它们不进入本机库，因此永远无法登录 |

读取失败（网络不可达、凭证无效、表 id 错误）时只记 warning 日志并跳过本次比对，**不影响服务启动**。

> 「自动比对」与「手工同步」是两件事：启动期这条链路只留痕、绝不建号；而管理员可以用第 9 节的
> `POST /api/admin/users/sync-from-feishu` 主动把这些账号补进本机（需要 `account.create` 权限，且只补本机没有的账号）。
> 也就是说"外部账号登不进来"的结论成立于**没有人执行过同步**的前提；同步是一个明确的管理动作，会留下 `user.sync-feishu` 审计。

## 8. 表格标识与网页地址（V2 容错）

这个项目里最容易出错的一步是**填表号**。飞书网页端地址栏里复制出来的是整条链接：

```
https://<你的租户>.feishu.cn/base/<app_token>?table=tblXXXXXXXX&view=vewYYYYYYYY
```

把整条链接当成 `table_id` 填进去，接口会带着错误路径去调飞书，症状是"接口全部失败 / 字段读不到"，
而错误信息不会告诉你"你填的是网址"。所以服务启动时会对这三个配置项做一次解析（`AppConfig.NormalizeFeishuTargets`，幂等：填干净的 ID 进去结果不变）：

| 配置项 | 容错行为 | 启动日志提示 |
| --- | --- | --- |
| `Feishu:AppToken` | 值里含 `/base/` 时，取其后到 `?`、`&`、`/`、`#` 之前的一段作为 base 标识 | `Feishu:AppToken 看起来是一条飞书地址，已自动取出其中的 base 标识。` |
| `Feishu:TableId` | 取 `table=` 之后到 `?`、`&`、`/`、`#`、空格 之前的一段；没有 `table=` 参数时按原值截断 | `Feishu:TableId 看起来是一条飞书地址，已自动取出其中的 table 标识。` |
| `Feishu:UserTableId` | 同上（典型场景是粘贴的地址后面还带着 `&view=…`） | `Feishu:UserTableId 后面带了视图参数，已自动截断（table_id 不含 &view=…）。` |

这些提示走的是启动警告列表，控制台逐行打印 ` [提示] …`，因此"我粘贴的是地址，为什么还能跑"与"我是不是粘贴错了"都能在启动日志里找到依据。

网页地址由两个独立配置项承载，用于前端「在飞书中打开原表」的跳转：

| 配置项 | 含义 | 未显式配置时的行为 |
| --- | --- | --- |
| `Feishu:TableUrl` | 报销单**原表**在飞书网页端的地址 | 若 `Feishu:AppToken` 与 `Feishu:TableId` 都在，按 `https://my.feishu.cn/base/{appToken}?table={tableId}` 自动拼一条；若 `TableId` 填的是整条地址，则留用其中的原始地址 |
| `Feishu:UserTableUrl` | **用户表**在飞书网页端的地址 | 同上，用 `Feishu:UserTableId` |

两者经 `GET /api/invoice/meta` 的 `tableUrl` / `userTableUrl` 下发给前端；启动横幅在它们非空时也会各打印一行（`报销单原表` 与 `用户表原表`）。
**服务本身不会去访问这两个地址**，它们只是给浏览器点的链接。

## 9. 账号同步（从飞书用户表补账号，只补不改）

镜像的方向是"本机 → 飞书"；账号同步是反方向"飞书 → 本机"，**必须由管理员在管理端手工触发**，不会自动执行。

| 动作 | 接口 | 需要的权限键 |
| --- | --- | --- |
| 只读预览 | `GET /api/admin/users/feishu-rows` | `account.list` |
| 执行同步 | `POST /api/admin/users/sync-from-feishu`（请求体 `{ dryRun, reason }`） | `account.create` |

**「同步只补不改」是这条链路的边界**，也是它能安全存在的前提：

| 场景 | 处置 |
| --- | --- |
| 本机没有该账号 | 新建，`origin = feishu-sync` |
| 本机已有该账号、本机缺 `record_id` | 认领对面的行（记下 `record_id`），之后本机改动会更新到那一行 |
| 本机已有该账号、本机已有 `record_id` | 完全不动：口令、角色、启停保持本机值，同步不改写本机口令散列 |
| 用户名不可用 / 对面用户名重复 / 操作者无权创建该角色 | 跳过，并在该行的 `detail` 里写明原因 |

为什么不让它覆盖：对面那张表协作方可以直接编辑。如果"对面改了、本机就跟着改"，那么改一行「角色」就等于改本系统的管理员；
只有坚持本机单方面权威，权限矩阵才挡得住外部输入。

字段口径（`FeishuMirror.ListAccountRowsAsync` 读对面，`UserService.ApplyImport` 写本机）：

| 对面用户表列 | 本机字段 | 转换口径 |
| --- | --- | --- |
| `用户名` | `userName` | 必填、不含空白与控制字符、长度 ≤ 64（比注册的 ASCII 用户名校验宽松，允许中文）；为空的行直接跳过 |
| `姓名` | `displayName` | 为空时取用户名，截断 32 字符 |
| `工号` | `employeeId` | 形如 `E` + 四位数字且不与本机冲突时沿用；冲突或没填则由本机新发 |
| `角色` | `role` | 「管理员」→ `admin`、「财务」→ `finance`、其余 → `employee`；**永不产生 `superadmin`** |
| `账号状态` | `disabled` | 含"停用"即视为停用 |
| `创建时间` / `最后登录时间` | `createdAt` / `lastLoginAt` | 对面没值时，创建时间取当前时间，最后登录时间留空 |
| `密码哈希` / `盐` | `passwordHash` / `passwordSalt` / `passwordIterations` | 见下表 |
| `record_id`（行标识，不是列） | `mirrorRecordId` | 记下来，之后本机镜像更新到这一行，而不是新建重复行 |

口令材料的换算（这条最容易踩坑）：

| 项 | 对面（协作方前端） | 本机 |
| --- | --- | --- |
| 算法 | PBKDF2-HMAC-SHA256 | 同 |
| 编码 | **十六进制** | **base64** |
| 迭代次数 | 与 `Feishu:MirrorPbkdf2Iterations` 对齐（默认 100000） | 导入时把该账号的 `passwordIterations` 记为同一个值（默认 10 万，而不是本机新建账号的 21 万）；登录校验按账号自己的这个值走 |
| 效果 | —— | 对方用他在对面前端用的**原口令**即可登录本系统，不必重新发口令 |
| 对面没有可用哈希（哈希不足 64 位十六进制或盐不足 32 位） | —— | 账号照样建，但标记 `needsPasswordReset`：管理员重置口令前登不进来 |

顺带一个方向对照：本机写向对面的镜像也走同一套参数（`FeishuMirror.HashForFeishu`，hex 编码、10 万次迭代），
所以"镜像写出去的哈希"与"同步读进来的哈希"是同一口径；区别在于镜像默认写的是**演示口令**的哈希（`demo` 模式，见第 4 节），
而同步读进来的是对方**真实在用**的那个口令的材料——这也是同步接口只给管理员、并且要留审计的原因。

同步的审计与失败语义：

| 情况 | 结果 |
| --- | --- |
| `dryRun = true` | 用当前账号库的只读快照跑同一套判断，只统计不落盘；审计 `user.sync-feishu` 记 `PREVIEW` |
| 执行成功 | 审计 `user.sync-feishu` 记 `SUCCESS`，明细含"读到 / 新建 / 认领 / 已存在 / 跳过 / 待重置口令"计数 |
| 从对面读到 0 行 | HTTP 409 `SYNC_UNAVAILABLE`，审计记 `FAIL`；可能是表还没建/还没数据，也可能是凭证或表号不对（读取失败按静默处理，具体原因见服务日志） |
| 未配置飞书（`FeishuConfigured` 为假） | HTTP 409 `SYNC_UNAVAILABLE`，不做任何本机改动 |
| 操作者没有 `account.create` | HTTP 403 `FORBIDDEN`，审计记 `DENIED` |

请求体、响应字段与完整错误码见 [API参考.md](API参考.md) 7.2；本机权威原则、角色映射边界与 `origin` 字段见 [账号与权限设计.md](账号与权限设计.md) 第 10 节。

> 读取只取一页（以代码为准）：同步走的是 `FeishuApi.ListRecordsAsync`，它不带分页游标，按 `page_size=200` 请求一次。
> 因此**对面用户表超过 200 行时，同步与预览只看得到第一页**（启动期的外部账号比对用的是同一个调用）；账号规模超过这个量级时需要分批处理或给该方法补翻页。

## 10. 配置步骤

1. 复制模板：

   ```bash
   cd AiApprovalServer/config
   cp secrets.local.example.json secrets.local.json
   ```

2. 在 `secrets.local.json` 里填值（真实凭证只放这里，不要写进 `appsettings.json`）：

   ```json
   {
     "Feishu": {
       "AppId": "<见 config/secrets.local.json>",
       "AppSecret": "<见 config/secrets.local.json>",
       "AppToken": "<见 config/secrets.local.json>",
       "TableId": "<见 config/secrets.local.json>",
       "UserTableId": "<见 config/secrets.local.json>",
       "TableUrl": "<见 config/secrets.local.json>",
       "UserTableUrl": "<见 config/secrets.local.json>"
     }
   }
   ```

   `AppToken` / `TableId` / `UserTableId` 三项目前**允许直接粘贴飞书网页地址**，服务启动时会自动取出其中的标识（见第 8 节）。
   `TableUrl` / `UserTableUrl` 只在"想显式指定前端跳转地址"时才需要填，留空即可（服务会按 `AppToken` + 表 id 自动拼一条）。

3. 该文件路径为 `<内容根>/config/secrets.local.json`，**已被 `.gitignore` 忽略**，不会随仓库提交。

凭证解析优先级（`AppConfig.LoadFeishu`，**自上而下取第一个非空值**）：

| 顺序 | 来源 | 形如 |
| --- | --- | --- |
| 1 | 环境变量 | `AISERVER_FEISHU_APPID`、`AISERVER_FEISHU_APPSECRET`、`AISERVER_FEISHU_APPTOKEN`、`AISERVER_FEISHU_TABLEID`、`AISERVER_FEISHU_USERTABLEID` |
| 2 | 本地密钥文件 | `config/secrets.local.json` 的 `Feishu.*` |
| 3 | 配置文件 | `appsettings.json` 的 `Feishu.*`（仓库里刻意留空） |

刻意让"本地密钥文件"优先于 `appsettings.json`，避免有人图省事把凭证写进会被提交的配置文件。
`config/secrets.local.json` 解析失败时会记入启动警告（`AppConfig.StartupWarnings`）并忽略该文件。

镜像是否启用（`AppConfig.FeishuConfigured`）要求 **`AppId`、`AppSecret`、`AppToken`、`UserTableId` 四项全部非空**；
不满足时镜像直接跳过（`mirrorState = skipped`），**账号功能没有任何影响**。

**未配置飞书也能正常启动**（已实测）：凭证为空时服务照常启动，启动横幅会打印

```
 账号权威   : users.json（本机 JSON）；飞书镜像 未配置（跳过镜像，不影响账号功能）
```

也就是说 `config/secrets.local.json` 只是"镜像功能"的可选文件：
- 交付/上传前**直接清空或删除它即可**（文件不存在也不会影响启动）；
- 删除后唯一的变化是：账号不再同步到飞书用户表，`POST /api/auth/register` 的响应里 `mirrorNote` 变成"未配置飞书，已跳过镜像（不影响本机账号）"；
- 想恢复镜像：把文件放回来（或设 `AISERVER_FEISHU_*` 环境变量）并重启服务即可。

## 11. 排障

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `mirrorState = skipped` | `FeishuConfigured` 为假：四项凭证有缺 | 补 `config/secrets.local.json` 或 `AISERVER_FEISHU_*` 环境变量 |
| 换票失败（`换取 tenant_access_token 失败 code=...`） | `app_id` / `app_secret` 不对，或应用被停用 | 在飞书开放平台核对应用凭证；错误信息里只有 `code`/`msg`，不含密钥 |
| 写入失败 `code=... msg=...`，提示字段不存在 | 飞书表列名与代码里的字段名不一致（多空格、错别字、缺列） | 按协作方的 `飞书字段对接手册.md` 逐字核对列名；表结构以飞书侧为准 |
| 单选字段写入报错 | 「角色」「账号状态」是单选列，写入了不在选项里的值 | 让飞书表的选项包含 `管理员` / `财务` / `员工` 与 `启用` / `停用`（逐字一致） |
| `429` / 频率限制 | 飞书接口限流 | 镜像本身是 best-effort，失败会记 `feishu.mirror.failed`，可在管理端重试；必要时调大 `Feishu:TimeoutMs` 或降低账号变更频率 |
| 请求超时 | 网络不可达、代理拦截、`Feishu:BaseUrl` 配错 | 检查出站网络与 `Feishu:AllowedHosts`；本地验收确认 `BaseUrl` 指向假飞书 |
| `出站主机不在白名单内：<host>` | `Feishu:BaseUrl` 的主机不在 `Feishu:AllowedHosts` 里 | 把该主机加入白名单（回环地址已默认放行） |
| 镜像成功但对面看不到 | 写到了另一个 base / 表（`Feishu:AppToken`、`Feishu:UserTableId` 配错） | 核对 base 与表 id；`Feishu:AppToken` 是**多维表格 base 的 id**，不是文件夹 token |
| 启动日志出现"Feishu:XXX 看起来是一条飞书地址…" | 配置里填的是整条飞书网页地址，不是纯 ID | 这是容错生效的提示（已自动取出标识，服务照常工作）；核对取出的标识指向的是不是目标表，也可以直接改成填纯 ID |
| `GET /api/invoice/meta` 的 `tableUrl` 为空 | `Feishu:TableUrl` 没填，且 `Feishu:AppToken` 或对应表 id 也缺 | 补齐 `AppToken` 与表 id（服务会自动拼地址），或直接填 `TableUrl` / `UserTableUrl` |
| 账号同步返回 409 `SYNC_UNAVAILABLE` | 未配置飞书，或对面用户表读到 0 行（表不存在/为空、凭证或表号不对） | 先用 `GET /api/admin/users/feishu-rows` 看 `configured` 与 `rows`，再核对 `Feishu:UserTableId` |
| 同步出来的账号"登不进去" | 对面那一行没有可用的口令哈希（该账号 `needsPasswordReset = true`） | 由管理员在管理端重置该账号口令，或让对方先在对面前端补全口令后再同步一次 |
| 演示口令拿不到 | 镜像模式是 `real` / `none`，或账号从未成功镜像 | 用 `GET /api/admin/users/{id}/mirror-password` 查看 `hint`；必要时切换为 `demo` 后重试镜像 |
| 启动日志出现"发现 N 个仅存在于飞书用户表的账号" | 飞书用户表里有本机不存在的账号 | 这是预期的防护留痕（审计 `feishu.mirror.foreign-account`）：不要在本机补建账号，除非确实要授权；它们当前无法登录 |
| 连着测镜像/越权用例后接口开始返回 403 | 本机 IP 已被自动封禁（越权创建账号与越权改角色各记 2 分、非管理员访问管理接口记 3 分，默认阈值 8 分） | 临时放宽 `Limits:WafStrikesBeforeBan`（例如环境变量 `Limits__WafStrikesBeforeBan=40`），或在管理后台「安全态势」里解封 IP |

## 12. 与协作方的字段契约

镜像只写**用户表**；报销单主表由本服务的 `/api/invoice/*` 写入口代理写（协作方前端改走这一层，不再直连飞书写主表），写完后协作方在其页面上看到的是同一张表的数据。

| 契约项 | 权威来源 |
| --- | --- |
| 用户表列名与列类型 | 协作方 `飞书字段对接手册.md` / `TABLE_SETUP.md` + 飞书表实际配置 |
| 「角色」「账号状态」的单选选项值 | 同上（必须含 `管理员` / `财务` / `员工`、`启用` / `停用`） |
| 镜像哈希参数（PBKDF2 迭代次数等） | 本服务 `Feishu:MirrorPbkdf2Iterations`（默认 100000），必须与协作方校验实现一致 |
| 账号同步方向的口令口径 | 对面 `密码哈希` / `盐` 的 hex PBKDF2 → 本机 `passwordHash` / `passwordSalt` 的 base64，迭代次数取 `Feishu:MirrorPbkdf2Iterations`（默认 100000）；见第 9 节 |
| 表格标识与网页地址 | base 标识与 table 标识由 `Feishu:AppToken` / `TableId` / `UserTableId` 提供（可直接粘贴网页地址）；跳转地址见 `Feishu:TableUrl` / `UserTableUrl`，第 8 节 |
| 本机账号字段与四角色矩阵 | [账号与权限设计.md](账号与权限设计.md) |

改动任何一侧的列名或枚举，都必须**同时**改飞书表与对应文档，否则镜像会失败（失败是静默的，只在管理端可见）。
