# 主服务器对接说明（前端 → 主服务器 → 飞书）

本文说明前端（小财奴网关）如何把**报销单写入口**交给主服务器 `AiApprovalServer`，
以及本地联调的两个进程怎么起、怎么验证。

---

## 一、为什么要接这一层

报销单的写入必须唯一，否则会出现三种不可接受的后果：

| 问题 | 直连飞书 | 走主服务器 |
| --- | --- | --- |
| 谁能写、写成什么值 | 前端自己判断，规则散落在业务代码里 | 服务端枚举白名单 + 金额区间 + 状态流转统一收口 |
| 申请人/工号是谁 | 前端传什么写什么 | 按登录令牌**服务端盖章**，前端伪造无效（实测覆盖成功） |
| 出错了能不能退 | 只能人工去表里改 | 每次写前存整行快照，管理员可按日志一键回退 |
| 事后能不能追 | 飞书表只剩结果 | 审计哈希链记录谁在什么时候改了什么 |

因此本仓库的做法是：**前端只负责"翻译与交互"，写库统一走主服务器**。

## 三、配置

```ini
# 主服务器地址；留空 = 不启用，保持直连飞书的老行为（登录也只用本地用户表）
BACKEND_BASE_URL=http://127.0.0.1:8899

# preferred：优先主服务器；只有"连不上"时才用本地用户表兜底登录、提交回落直连飞书（默认，演示用）
# required ：必须走主服务器；主服务器拒绝或连接失败都直接报错，绝不绕过（生产建议）
BACKEND_MODE=preferred

BACKEND_TIMEOUT=15
```

两种失败语义是**刻意分开**的，登录与提交都按这个口径处理：

| 失败类型 | 例子 | 行为 |
| --- | --- | --- |
| 业务拒绝 `BackendRejected` | 口令错误、账号被禁用/锁定、限流；以及提交时的无票阻断、部门不在枚举内、金额越界、事由缺失 | **绝不回落**，把服务端文案原样回给用户 |
| 基础设施故障 `BackendUnavailable` | 主服务器没起、超时、会话过期 | preferred 用本地用户表兜底登录 / 提交回落直连飞书（只影响这一笔）；required 直接报错 |

> 关键点：业务拒绝如果回落，等于"规则说不该写，却绕过写入口写进去了"——
> 审计与快照一起被绕过；登录同理，口令判定一旦回落，账号权威就不在主服务器了。所以只有连不上才允许回落。

> 推荐生产配置：`BACKEND_MODE=required`。此时本机用户表只作为离线演示的兜底，真正决定"谁能登录、能做什么"的是主服务器。

## 四、本地联调：两个进程

### 1) 主服务器（先起，因为前端登录时会先请它判定口令）

```powershell
cd <仓库>\AiApprovalServer
Copy-Item config\secrets.local.example.json config\secrets.local.json   # 填真实飞书凭证（已 gitignore）
dotnet run
```

启动日志里应看到：

```
 用户前端   : http://127.0.0.1:8899/
 财务工作台 : http://127.0.0.1:8899/finance
 账号权威   : users.json（本机 JSON）；飞书镜像 已启用（demo 口令模式，失败静默）
```

### 2) 前端网关

```powershell
cd <仓库>\xiaocainu
python -m venv .venv
$env:PYTHONUTF8 = '1'                      # requirements.txt 是 UTF-8，GBK 环境必须先开这个
.\.venv\Scripts\python.exe -m pip install fastapi uvicorn
.\.venv\Scripts\python.exe -m api.main 127.0.0.1 8000
```

浏览器打开 `http://127.0.0.1:8000/`（不要用 `0.0.0.0:8000`）。

> 前端同学机器上的 `run_server.bat` 里写死了他那台机器的 venv 路径，
> 换机器后要么改这个路径，要么直接用上面两条命令。

### 3) 验证三跳

| 跳 | 验证方式 | 期望 |
| --- | --- | --- |
| 前端 → 主服务器 | 前端登录一次，看返回体里的 `backend` 字段 | `主服务器已校验（角色=员工，工号=E0001）`（被本地表兜底时会显示 `本地用户表校验（主服务器未启用或不可达）`） |
| 主服务器 → 飞书 | 主服务器 `/finance` 页面看单据列表 | 能看到飞书主表真实数据 |
| 前端 → 主服务器 → 飞书 | 前端对话框里说完整一句单（部门/类型/金额/票据/事由），确认提交 | 答复里带 `BX-` 单号；飞书主表出现该行，且「申请人」「工号」是登录人本人 |

## 五、字段与枚举口径

前端**不需要**传这些（传了也会被服务端覆盖）：`申请人`、`工号`、`记录提交时间`、`合规结果`、`风险摘要`、`状态`。
`单号`由飞书自动编号生成，主服务器写完会回取并返回 `bill_no`。

前端需要传的字段（枚举以 `GET /api/invoice/meta` 为准，不要手抄）：

| 字段 | 说明 |
| --- | --- |
| `department` | 部门（11 个枚举） |
| `rtype` | 报销类型（差旅费/招待费/办公用品/交通费） |
| `amount` | 金额，0.01 到 100000 |
| `reason` | 事由，2 到 200 字（**必填**：服务端会拒绝空事由） |
| `hasInvoice` | 票据状态（有票/无票/未提）；无票会被阻断 |
| `city` | 城市（差旅费必填，37 个枚举） |
| `invoiceDate` | 发票日期，适配器会把 `2026/10/3`、`2026年10月3日` 等归一为 `YYYY-MM-DD` |
| `invoiceInfo` | 发票号码；销售方（可选，OCR 结果） |

日期统一由适配器归一，前端继续用它原来的写法即可。

## 六、顺手修掉的网关 bug（否则起不来）

`models/users.py` 里原先是 `from ..security.auth import hash_password, verify_password`。
项目根 `xiaocainu` 没有 `__init__.py`，`models` 与 `security` 都是顶层包，
双点相对导入会直接抛 `ImportError: attempted relative import beyond top-level package`，
**整个网关在 `import models` 阶段就崩**。现已改为"先试相对导入、失败回退绝对导入"。
另外 `requirements.txt` 含中文注释，在 GBK 默认编码的 Windows 上 `pip install -r` 会解码失败，
装依赖时先设 `PYTHONUTF8=1`（或直接用 `pip install fastapi uvicorn`）。

## 七、回退与排障

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 登录返回 `backend: 本地用户表校验（主服务器未启用或不可达）` | 主服务器没起 / 地址不对（`preferred` 模式下的离线兜底） | 起主服务器，核对 `BACKEND_BASE_URL`；生产环境建议把 `BACKEND_MODE` 设为 `required`，让这种兜底直接失败而不是悄悄换成另一套账号体系 |
| 登录直接报"用户名或口令错误" | 主服务器明确拒绝（口令错、账号停用、账号锁定、限流） | 这是最终结论，不会回落；按提示找主服务器管理员核对账号 |
| 登录报"主服务器登录失败，已按 required 模式拒绝登录" | `required` 模式且主服务器不可达 | 起主服务器，或临时切 `preferred` |
| 提交后答复是"这张单没有提交成功：…部门必须…" | 业务规则拒绝（不回落） | 按提示改数据后重新确认提交 |
| 提交后答复"主服务器暂时不可用" | required 模式且主服务器不可达 | 起主服务器，或临时切 `preferred` |
| preferred 模式下同一笔单出现两行 | 曾经回落直连飞书写过一次，之后又走主服务器写了一次 | 只看主服务器写入的那一行（有审计与版本）；建议生产用 required 模式杜绝 |
| 想看某笔单能不能回退 | 主服务器写入口每次都存快照 | 管理后台「版本与回退」按日志回退；删掉的行会按快照重建（单号由飞书重新分配） |

## 八、账号权威边界（谁说了算）

账号的权威在**主服务器**：登录先由主服务器判定口令，飞书那张用户表是主服务器写出去的镜像。
这条边界决定了日常操作该怎么做：

| 事项 | 正确做法 | 为什么 |
| --- | --- | --- |
| 登录判定 | 网关先调主服务器 `POST /api/auth/login`，由它决定放不放行 | 口令错误、账号停用、锁定、限流都直接失败，不再回落到本地用户表 |
| 新增账号 | 主服务器管理后台「账号管理」创建 | 创建时主服务器会一并把账号写进飞书用户表（含可用口令哈希），工号由主服务器自增分配 |
| 用 `tools/user_admin.py add` 直接往飞书表里加一行 | 只对飞书表生效，**登录不了主服务器**；需要管理员在主服务器点一次「同步缺失账号」把它导入进来 | 登录权威在主服务器，表里多一行不等于开户 |
| 改角色 / 停用 / 重置口令 | 主服务器管理后台操作 | 主服务器改完会把变更写回飞书表对应行，两边保持一致 |
| 账号同步的口令 | 对面表里的口令哈希（hex，PBKDF2-HMAC-SHA256 10 万次）会被原样导入主服务器 | 对方用原口令即可登录主服务器，不必重新发口令；该账号在主服务器首次登录成功后口令存储会自动升级 |
| 角色 | 主服务器有四个角色（超级管理员/管理员/财务/员工），飞书表只有三个选项（员工/财务/管理员） | 对面写「管理员」导入后是**管理员**，永远不会变成超级管理员 |

主服务器侧对应接口：`GET /api/admin/users/feishu-rows`（只读预览）与
`POST /api/admin/users/sync-from-feishu`（同步，`dryRun` 可先预览）。同名的账号一律不动，
所以不会出现"对面改一行就把主服务器账号口令改掉"的情况。

唯一的例外是"主服务器连不上 且 不是 required 模式"：这时网关会用本地用户表兜底登录（离线演示用），
这种账号没有主服务器会话，提交会回落直连飞书——所以生产环境请把 `BACKEND_MODE` 设为 `required`。
